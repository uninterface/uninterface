# List presentation and editable-collection contracts

[List contract](list.md) · [API proposal](list-api.md)

The source/control and column-binding APIs are implemented. UiList, UiTable, UiTableColumn and UiPaginator are implemented across supporting backends. The editable-collection bridge coordinates parent values. Native table SSR/hydration, browser interaction and assistive-technology support depend on the selected backend’s documented envelope.

## Column composition and typing

UiTable accepts synchronous column declarations in ordinary Vue composition, including fragments, conditional declarations, keyed loops and reusable business column components. Each declaration registers itself with the nearest table. The table does not open a business component's render function or inspect its internal Vue tree. Dynamic declaration order follows actual declaration-anchor order; cells are keyed by column and business item identity.

The private declaration host is noninteractive, hidden and excluded from accessibility. It renders before the visible surface so synchronous declarations are available during SSR. It owns its ordering observer and releases it on view removal. These are core/backend coordination obligations, not business-authored markup. Backends remain responsible for their actual table and cell DOM.

Async setup/Suspense columns are unsupported in this initial contract: a declaration arriving after the SSR surface has rendered is a hard error. Preload column code/data before rendering, or deliberately add a synchronous declaration after hydration. Awaiting server data in a page does not permit half-rendered table headers. Teleporting declarations out of the host is unsupported. Arbitrary business cell content remains opaque and may use normal Vue composition.

Direct declarations use a Vue `@vue-generic` annotation to state the item/filter/sort types for their slots. A parent table's binding does not automatically infer its independent child declarations. Bound declarations infer types from [UiTableColumnBinding](../api/types/UiTableColumnBinding.md). Neither route requires consumer `any` casts, a data accessor or a separate table controller. [UiListSlotProps](../api/types/UiListSlotProps.md) is the shared `{ item, context }` payload; no second `value` is provided.

Column keys must be unique and stable. Use keyed remount for an identity change. Reactive labels/query associations are allowed; query associations are independent of cell content. Binding and local definition props are mutually exclusive. A column bound to another collection is rejected. A missing nonempty label and missing label slot is rejected; the business must keep a rich label slot meaningfully named and noninteractive.

Acceptance: first SSR response and hydrated header order agree, no hydration warnings, two request-local tables remain isolated, direct/reusable conditional columns reorder correctly, raw mounted editor drafts survive label/order updates, and invalid query/slot types fail compilation.

## Column sizing and alignment

Implemented on direct and bound declarations: preferredWidth, minWidth, spring, resizable and left/center/right align. Widths support explicit lengths or content measurement, including native cell insets. Defaults are 12em/3em/true/true/native. At least one spring column is required. Shared allocation and adjoining-boundary redistribution preserve total width and minima; horizontal scrolling requires explicit permission. The implemented impossible-fit fallback hides the mounted table behind a localized recoverable status while retaining drafts. This fallback is an implementation choice, not a previously selected user preference. Business authors supply responsive configurations that fit their actual controls.

See [the public sizing guide](../guides/table-columns.md) for ownership, defaults, units, keyboard/pointer interactions, width lifetime and backend obligations. Unit/DOM checks cover supporting backends; real-browser geometry remains unverified in the restricted development environment. Some native integrations can recreate editors during column reorder; consult backend documentation for identity limits. Sizing/alignment updates preserve editors.

## Header sorting and filtering

Sortable source keys and single-level versus multi-level support are independent declarations owned by the business integration and bounded by actual source capabilities. See [sorting capabilities](../guides/collection-sorting.md) for the agreed requirements, execution ownership and implementation gaps. The sorting interactions below describe the currently implemented multi-level behavior; they do not establish that every remote source supports it. Explicit single-level configuration/enforcement remains pending.

Prefer the toolkit's native sortable-header interaction when it can preserve shared query ownership and ordered multi-sort semantics. Sorting must not turn the column label into an ordinary action button visually: retain the surrounding header's font, weight and size across sortable, unsortable and sorted states. Native sort indicators and focus/hover treatments may distinguish interaction/state. Where native header behavior is unavailable, use a keyboard-accessible control with header typography and no ordinary button chrome. Use common semantic sorting artwork for composed indicators; native integrated carets/icons remain toolkit-owned. No business-side CSS is required.

A sortable header cycles absent → ascending → descending → absent. A newly added clause goes at the end of the ordered sort query. Cycling an existing clause changes/removes it in place and preserves other clauses. One activation is one atomic source request using `binding.setQuery`; filter/sort transitions restart pagination. No shift-key or silent replace-all policy is required.

Native directional carets may request ascending/descending/removal directly rather than cycling. That intent changes only its clause, retains its precedence, and causes no new read when the accepted direction is unchanged. Native single-column state must not silently discard other shared clauses.

The table's primary sorted header carries native `aria-sort`; secondary sorted headers expose localized direction and precedence in their sort action's accessible description. Headers without a sort association have no implied action. Nested filter input and column-resize events cannot activate header sorting. Backend sort echoes must not generate another request.

`filterBy` associates meaning, not a generated editor. A header filter icon opens a nonmodal, anchored popover. Its `#filter` slot receives `{ filters, setFilters, close }`, with concrete `Readonly<F>` types and whole-filter replacement. The slot builds its business editor using existing controls. External filters use the identical query and request operation. Explicit apply/debounce behavior belongs to that business filter composition; Uninterface does not infer it from an arbitrary predicate.

Business supplies `filterActive`; core never infers active state from arbitrary values. Opening/closing the popup never applies criteria. `close()` lets an editor dismiss after its chosen commit, while Escape/outside/trigger dismissal preserves the query. Cross-column and special filters belong in a separate business section. Non-table views also place sorting there. `UiListControl.hasColumnSort` / `hasColumnFilter` react to mounted, active table declarations and backend support; they describe presentation availability, not active query state. See [column filtering](../guides/column-filtering.md).

Acceptance: external/header updates stay synchronized, secondary clauses survive cycling, one action issues one request, fields remain keyboard-accessible and arbitrary cell content never supplies an implicit accessor/filter function.

## List/table allocation and continuation

The selected UiList props are `columns?: number`, `columnWidth?: string`, `height?: 'content' | 'full'` and `scroll?: 'none' | 'horizontal' | 'vertical' | 'both'`. Omitted grid props mean a vertical list. `columns` requests an exact positive count; `columnWidth` requests a preferred minimum width, fitting equal-width peers and shrinking to one available-width column when needed. They are mutually exclusive. `columnWidth` accepts a positive `rem`, `em` or `px` length, not arbitrary CSS expressions. Theme-owned peer separation supplies ordinary gaps; no card/inset is inferred.

Height defaults to content and scrolling to none. Full height/vertical scrolling consume a definite parent allocation; no viewport/pixel height is invented. Scrolling follows UiLayout's keyboard, actual-scrollport naming, overflow reachability and focus-clearance guarantees. UiTable uses the same height/scroll contract; its backend keeps wide column content reachable. Table accessible naming targets the actual table; scroll-region naming targets the actual scrollport. Supplying one label does not excuse putting it on the wrong target.

`infinite?: boolean` enables near-end observation only for an accumulation-capable list binding. Initial loading remains owner-driven. Core coordinates intent and budgeting; the backend observes its actual bounded scrollport/sentinel and handles visibility. Automatic continuation is limited to three successful chunks per uninterrupted near-end episode. Leaving/re-entering the threshold, an actual user scroll or a viewport resize starts another episode; repeated observer notifications alone do not reset it. A new filter/sort/size generation resets the budget. Infinite presentation has no Load more action. Further wheel, touch or keyboard scroll intent renews the budget, even at an underfilled boundary. Failure requires explicit Retry; terminal metadata stops continuation. Hidden/deactivated views pause, unmount disconnects, and remount never restarts the initial read.

Acceptance requires a real browser: count/width grids, bounded/horizontal overflow, narrow/touch/zoom, retained focus/reading position on append, underfilled viewport budget, no failure loop, hidden/reactivated observation and cleanup. Prototype DOM checks do not establish these geometry outcomes.

## Collection card-grid width preferences

UiCollectionView accepts optional `presentationOptions: UiCollectionPresentationOptions` for `cards-grid`. Ordinary use and an empty object receive backend default preferred minimum and finite maximum. Explicit min/max bounds override them; minimum-only input requests no maximum and retains occupied-column stretch, including a lone full-width item. Maximum-only uses the default minimum; `maxWidth: 'default'` keeps the default maximum with a custom minimum. Undefined follows omission. These are direct view properties, not list-controller state or a strategy requirement.

Lengths are positive finite rem/em/px. Core rejects invalid keys/lengths and reversed same-unit ranges; backends resolve mixed units/defaults and reject a resolved maximum below minimum. Minimum is preferred: narrow allocations permit one shrinking column. Maximum includes the card frame. Bounded columns are counted from available width/minimum/gap independently of item count; equal widths stop at maximum subject to the single-column exception below, partial rows retain columns, ordinary gaps remain intact and surplus stays at logical end. Minimum-only collapses empty columns and distributes remaining width among occupied columns. Table and full-width cards ignore the dimensions.

Backends own markup, defaults, gaps and measurement targets; all five initially provide 20rem/25rem defaults. Optional shared allocation mechanics handle container changes, rem/em resolution, activation and cleanup without remounting item content or reading the source. Server rendering preserves content with a bounded CSS fallback; measured client packing can change initial column count. See the [business guide](../guides/collection-views.md#card-grid-width-preferences), [type reference](../api/types/UiCollectionPresentationOptions.md) and [backend obligations](../api/backend/collections.md#card-grid-width-allocation-mechanics).

Acceptance: sparse/full/partial counts, bounds and min-only reset, narrow overflow, logical alignment, container/font changes, keyed draft/focus retention and observation cleanup. Browser automation is separate from human visual and assistive-technology acceptance.

`stretchSingleColumn?: boolean` defaults to true: when the offered width permits only one column at the effective minimum/gap, ignore the maximum and fill the available width. Explicit false retains a strict maximum. This depends on container column capacity, not record count or partial-row occupancy; a single item in a multi-column allocation stays capped. A flag-only object retains ordinary default bounds, and minimum-only growth is unaffected. Initial server/premeasurement fallback remains bounded until client measurement resolves capacity. Verify threshold transitions and reactive opt-out/reset with stable drafts/focus and no source reads.

## State, slots, announcements and focus

Every collection presentation distinguishes uninitialized, initial loading, successful empty, retained refresh, append loading, read/append failure and stale reconciliation. Error slots receive `{ error, placement, retry, canRetry }`; empty slots receive no fabricated record. Status customization cannot reinterpret failure as empty success or invoke a second source path. Built-in wording is localized; exception strings are not automatically public messages. Ordinary successful collections have no persistent visible loaded-item summary by default; showSummary is an explicit opt-in. A paginator or custom table footer can supply a useful count. This does not suppress accessibility announcements or loading/empty/stale/error/completion feedback.

Views share one logical announcement coordinator per list binding and Vue application. It chooses one active visible host for collection status, tracks already-announced transitions, and transfers hosting without replaying an old result. Paginators do not independently repeat collection status. App isolation and SSR cleanup are required. Item operation feedback stays attached to that item's action. Generic completion/dismissal controls are not added without a purpose.

Removing a focused item recovers focus only in the view that contained focus: first available action in the next surviving item, then the previous item, then the named collection target. If focus has already moved elsewhere while an async request finishes, do not steal it. Selection is a dedicated control, activation is explicit, and nested actions/editors do not implicitly activate or select a row. A table with editors remains an ordinary table unless a separate grid interaction contract is introduced.

Acceptance: names target semantic elements, accessible state follows actual action availability, only one shared status announcement occurs, simultaneous views do not compete for focus, removal retains an operable destination, and keyboard/focus paint is verified in each backend.

## Paginator optional presentation

UiPaginator renders only first, previous, pages, next and last. UiPaginatorSizeSelect and UiPaginatorJumper are independent controls borrowing the same binding. They are placed by application layouts, not paginator slots. There are no showTotal/showRange/showPageSize props. Applications render optional statistics as localized ordinary text from readonly total/range/pageCount/accepted/requested metadata.

Zero matches have no active page; cursor sources never invent page numbers. Bounded native page buttons require known positive bounds and configured jumps. First/previous/next/last remain present and disable unsupported routes. Last requires known numbered bounds and jumps. Out-of-bounds retained pages must not cause native auto-clamping requests. Source reconciliation remains owner-owned.

The size selector uses the session's allowed numeric choices with localized count-per-page labels. The jumper owns a temporary text draft, commits on Enter/blur and validates positive safe whole numbers within known bounds. Enter prevents form submission and respects IME; its following blur must not issue a second request. Failed jumps retain the draft; explicit Enter can retry, while blur cannot automatically retry. Pending/disabled/unsupported states block live activation. No component loads on mount or disposes its owner.

All pagination control surfaces have the same or similar ordinary height within a backend. Jumper labels sit inline; native sizes and densities are preferred to fixed shared dimensions. Validation feedback may extend beneath the row. Verify independent mounting, shared state, known/unknown/cursor/empty cases, raw draft retention, error association and request counts. Browser checks must compare actual control heights and keyboard/focus behavior separately from DOM assertions.

## Parent-value bridge

The implemented bridge is a factory-created `createUiListValueControl` session. See [editable collections](../guides/editable-collections.md) for usage and obligations. Its business owner supplies typed initial items, stable identity and `createEditor(item)`. Each editor exposes one record-valued field control and `dispose`; it may internally compose codecs/fields. Ordinary consumers of the encapsulated invoice editor supply initial invoice data and a save callback, without constructing those internals.

The bridge contributes one collection-valued field to the parent form. It owns keyed child editors, claims child coordination exactly once, and keeps their private raw drafts outside the parent form's fixed field inventory. List/table views borrow those editors and a local source projection; filtering/paging never removes children from full validation/submission. Source results are not another editable draft.

Membership operations are `insert(item, { before? })`, `remove(key)`, `replace(key, item, { discardDraft? })` and `move(key, { before? })`. They operate on full keyed order, not visible indices. Duplicate keys and unsupported replacements fail before changing membership. Replace preserves identity; replacing dirty raw input requires explicit `discardDraft: true`. Moves preserve child editors. Parent reset restores accepted membership/order/values/feedback and disposes only removed editors. Membership changes must be staged so editor-construction failure cannot partly alter the collection.

Child revision changes invalidate the aggregate field, whole-form validity and pending save snapshots, even when hidden. Parent validation runs each distinct child once and includes its rules/composition checks. It must not mutate the outer draft/baseline from a check. Private child validation without normalization is available internally so codec normalization does not invalidate the parent mid-pass. Typed projection may retain last valid values while raw input is invalid; calculations must distinguish that condition.

Parent effective locks propagate as independent child operation locks. Never overwrite or save/restore business-disabled flags. Removed/disposed child validation cannot publish into the remaining session. View removal does not dispose editors. Self/cyclic participation and a child already claimed by another coordinator are rejected.

Canonical save acceptance uses implemented `form.submit(save, { accept: (result, submitted) => canonicalModel })`. The synchronous mapper runs inside the guarded submission while locks remain held; every field formats before baselines are changed. It must be pure and return a complete typed model. Returned data is authoritative, so the mapper owns domain adaptation/validation. Same keys reuse editor instances on acceptance. A changed temporary key is treated as accepted removal plus insertion: the old editor is disposed once, the canonical editor starts clean, and obsolete callbacks cannot target it. Applications needing retained identity across persistence should use a stable local identity distinct from server IDs. No unfinished draft is automatically merged into canonical data.

External replacement during dirty editing defaults to a conflict, not silent merge. The business may deliberately discard/restart through an explicit operation or keyed session replacement. Programmatic draft changes during save make the old attempt obsolete. Parent Save never invokes independent per-child persistence.

The bridge reports the first invalid child key in full order. A business-supplied asynchronous reveal callback clears restrictive filters/selects its page and awaits rendering; only then does the view focus that child's first invalid editor. If the item disappears or the session changes during reveal, cancel recovery. This callback coordinates presentation and does not grant the bridge ownership of business filters or DOM focus mechanics.

Acceptance: hidden invalid raw drafts block parent Save; table/card swaps retain them; full saved/reset membership is independent of query projection; locks preserve business restrictions; removed async validation is obsolete; same-key canonical acceptance reuses editors; temporary-to-canonical replacement cleans up once; reveal precedes focus. For a complete invoice workflow, verify paginated reference keyword search on the outer invoice list, independent modal editor sessions, all line items in an editable table, and full validation/save/reset. Line items have neither search nor pagination; hidden-invalid behavior remains a general collection-bridge acceptance requirement rather than an invoice search feature. Verify reveal/focus in a real browser and with assistive technology.


## Independent overflow axes and bounded height

UiList/UiTable default to content height, yielding vertical scrolling to their parent. Full height consumes an existing bounded allocation and automatically enables vertical scrolling. Horizontal scrolling is separately permitted by horizontal/both; it is never implied by bounded height. Backends implement explicit overflow-x/overflow-y policies, not a two-axis overflow shorthand. Full-height tables automatically enable native fixed/sticky headers where available, with backend-owned sticky presentation for plain HTML tables. Supporting backends implement header pinning. Declared data summaries also remain visible at the bottom of the bounded record viewport; card summaries occupy a separate supporting surface outside their record scrollport. Content-height collections remain in normal flow. See the collection-summary guide for label spans and business calculation ownership. Headers remain horizontally aligned, and changing allocation preserves the mounted collection/session. See the public list guide's mode matrix and acceptance checks.

## Specialized creation row

UiTable optionally accepts an ordinary UiButtonBinding through addRow and a localized addRowLabel. It presents a backend-generated line of tinted column content areas inside native cell insets with one overlaid text-variant action after data rows and before the summary. The business owns actual draft construction, insertion, availability and focus; the preview never enters the source, item contexts, selection, counts or validation. No cell template introspection or sample editor session is permitted. Omission preserves ordinary table behavior.

The action composes its producer's disabled/loading state with live collection disabled/busy restrictions. It cannot use native submit/reset semantics. focusAddRow exposes enabled-action recovery without insertion. Backends preserve column geometry and accessible single-action interaction, including narrow scrolling. The creation affordance is the final body row in normal vertical flow, never a pinned footer. It scrolls with records, while a declared summary retains its independent bottom position. Short offers may release header pinning. Native targets and paint remain backend-owned. See the public UiTable reference and editable-collection guide for author obligations and observable checks.

Infinite continuation message content is customizable through `infinity-loading` and `infinity-complete` slots shared by collection/table/list views. Core owns state selection and source completion; backends retain indicators, semantic containers, continuation placement and the observation sentinel. Per-view plain-text message overrides supply defaults and the elected announcement; arbitrary slot VNodes are not an announcement source. See the [authoring contract and verification](../guides/collection-views.md#infinite-continuation-content).
