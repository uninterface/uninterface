# Date and time input family


## Control and optional field presentation

The current direction is a temporal control with reusable target bindings, superseding a configuration-only paired codec/binding helper. Factories are createUiDateControl, createUiTimeControl and createUiDateTimeControl. Each composes one existing field owner with temporal codec, eligibility and editing coordination; it does not maintain a competing selected-value state. See UiTemporalOptions and UiTemporalInputBinding in the API reference for exact types.

Each control exposes its field for form participation and target-specific bindings such as bindings.dateInput, bindings.timeInput or bindings.dateTimeInput. UiField is optional presentation. A bound standalone input gets its value, validation and semantic editing context from the control, without depending on an enclosing UiField. The application supplies an accessible name on the actual editing target and presents relevant validation feedback when UiField is absent. Composite/range views must preserve a meaningful group name and localized endpoint names. The same field description associations reach the endpoint editors.

With UiField, its field must match the binding's owning field; mismatches must be rejected rather than selecting one owner implicitly. Without UiField, the same field can still be registered with UiForm's control: form participation is independent of wrapper presence. Standalone use does not imply an additional component v-model or require a form. Existing input APIs are unchanged.

Views own focus, popup/highlight state and presentation. Controls own temporal semantics and validation coordination. Multiple compatible views may borrow one control intentionally; concurrent unfinished editing sessions require explicit coordination to avoid lost drafts or validation against stale values. Business owners control lifetime; a borrowing view must not dispose a shared control on unmount. Custom views can consume public target contracts without depending on the concrete factory.

## Values, codecs and presentation

Date values use canonical date strings such as `2026-10-20`; time values use strings such as `09:30` or `09:30:45` under an explicit precision contract. Local datetime values use strings such as `2026-10-20T09:30`; instant representations and timezone context must be distinguished explicitly. No backend date-library class becomes the required public value type.

The user's selected datetime direction is no zone suffix for local datetime and `Z` for UTC. Numeric-offset input remains a separate acceptance decision; it must never be misclassified as local simply because it lacks Z. Strong codec support should provide business-side Date objects and Unix seconds/milliseconds as explicit output choices. Date stores an instant, not the originating timezone; a local datetime requires a configured zone to produce an instant safely, and the zone remains separate context. Never infer timestamp units from magnitude. Date-only/time-only codecs must not invent a timezone/date merely to return Date objects. Date business-value round trips and field snapshots are covered by control tests.

The existing UiField/UiCodec model owns interpretation, validation, dirty/reset behavior and accepted values. Provide reusable codec support for strict calendar/time validity, precision, configured timezone conversion and ranges. Business compositions encapsulate this configuration; ordinary consumers should not rebuild date parsing or conversion. Native toolkit coercion must not define the business value.

Displayed date/time is a view-owned projection of the represented value. Locale, date order, separators and hour-cycle presentation do not redefine its canonical representation. UiTemporalPresentation provides optional locale and hourCycle preferences; the backend owns actual appearance and localized editing. Business codecs parse the fixed-format temporal representation into business values and format back to that representation. Arbitrary display format/parse adapters are not part of the public API. Decoding localized edits produces canonical candidate/draft information for semantic codec validation. An opaque codec does not implicitly supply picker eligibility or display-timezone context; a shared definition or paired binding must coordinate these without duplicating rules.

Unfinished/invalid editing must remain distinguishable from empty input and intentional open endpoints. Views may retain interaction drafts, but every relevant change must participate in field invalidation, dirty state, reset and submission checks. The previous valid value must not be submitted while a conflicting unfinished edit is displayed. Invalid strings remain field drafts and fail parsing before submission. Presentation changes must not silently truncate precision or reinterpret unfinished input.

User direction allows temporal-field dirty state to track changes in the resulting semantic value rather than every textual edit. Invalid input still invalidates the field and blocks submission even if no new semantic value exists and dirty remains false. This is scoped temporal design, not a change to existing global field dirty behavior. Temporal dirty comparison normalizes valid drafts; invalid drafts compare structurally. An explicitly configured default time may complete a date-only UiDateTimeInput edit; it must pass the same zone and eligibility validation. Malformed or partially supplied time must not be silently replaced with the default.

Agreed interpretation: omitted seconds mean zero and omitted fractions mean zero where supported. This does not authorize truncating supplied seconds/fractions when changing display precision. Canonical equivalence between minute and second spellings must be reflected in codec normalization and semantic dirty comparison. The user also accepted explicit default-time completion, resulting-value dirty tracking and Date/Unix-seconds/Unix-milliseconds codec direction with the timezone qualifications above. Codec factory signatures are documented in the per-export references.

## Datetime timezone context

Within this family, local-time-to-instant ambiguity concerns datetime; date-only and time-only values do not implicitly acquire a timezone. A local datetime need not denote an instant. If converting it, timezone interpretation, view projection and date/time eligibility must share explicit context.

Recommended zone forms are an IANA region identifier, UTC or an explicit fixed offset. Named zones include their own seasonal/historical rules; a daylight-saving boolean is not a replacement. Repeated and nonexistent local times need a defined resolution policy. An explicit offset supplied with a named zone must be consistent with that zone at the selected local datetime; it cannot make a nonexistent time valid. Rejecting conflicts is the recommended starting policy. Exact zone/disambiguation APIs are not yet agreed.

## Ranges

Date-only ranges are **[start, end]**, inclusive at both ends. A date range from `2026-10-20` to `2026-10-21` includes both days; equal dates mean one included day. If a business operation needs an equivalent datetime interval, use midnight of the start date through **excluding midnight after the end date**, in its explicit timezone. This includes fractional seconds without manufacturing a last instant such as 23:59:59.

Time and datetime ranges are **[start, end)**, start inclusive and end exclusive. A datetime interval ending at midnight excludes that midnight. Equal datetime boundaries form an empty interval, accepted only with `allowEmptyRange`.

A range represents one business field and one coherent UiInputFrame, even when the backend renders two editors. Ranges use named start/end members with the range option on the control. Unrelated date/time fields need not become a range.

Bounded time ranges use ordinary clock editing: an end clock at or before start means the following day. Equal clocks mean 24 hours, not an empty interval. The start must be within the clock day and duration must be positive and at most 24 hours. Canonical extended-hour ends preserve day displacement: `[22:00,26:00)` represents 22:00 to 02:00 next day; `[00:00,24:00)` represents a whole clock day. The backend shows ordinary end clocks with a next-day indication. Longer spans use datetime or another representation. A zoned midnight-to-midnight datetime interval need not last exactly 24 elapsed hours around offset transitions.

Both boundaries are specified by default. A leading boundary-mode selector offers both specified, start only, end only and unrestricted, filtered by `allowOpenStart`, `allowOpenEnd` and `allowUnrestricted`. These modes describe whether boundaries exist; they do not change endpoint inclusion. Hidden endpoint drafts survive mode switches; reset, Clear and external replacement discard retained drafts. Unfinished supplied text remains invalid, never implicitly unbounded. Backends prioritize native range controls for bounded mode and scalar controls for one-sided modes. Native partial models do not establish intentional-open semantics.

Agreed representation: `null` for an empty whole field; `{ start: value, end: null }` for an intentionally unbounded upper end and `{ start: null, end: value }` for an intentionally unbounded lower end. Null endpoints are valid only when the corresponding policy permits them. `{ start: null, end: null }` means an unrestricted interval, not an empty field, and is rejected unless explicitly enabled. Invalid/unfinished endpoint drafts must not be encoded as a valid null endpoint. Avoid Infinity, empty strings and sentinel dates as open-bound values.

## Allowed and disallowed values

The requested family must support allowed/disallowed values. Datetime rules may apply to the date, time or full datetime, including date-dependent time availability. Interpret them in an explicit agreed value/zone domain, not whichever timezone the browser happens to use. Supply one semantic definition to both field validation and view eligibility; disabling picker cells alone is insufficient.

User-proposed input forms are explicit value-to-boolean decisions or a function. Recommended shape: a finite `values` map with explicit `otherwise` fallback, or a synchronous boolean predicate over canonical values. This allows a short allowlist (otherwise false) or denylist (otherwise true) without enumerating the whole domain. UiTemporalEligibility defines these forms. Compose date, time and datetime decisions explicitly; the existing recommendation is conjunction, with denial taking precedence. Async availability requires separate loading/error/cancellation behavior rather than accepting promises in synchronous picker predicates. The same rule definition feeds view eligibility and field validation; the view cannot turn an invalid business value into a valid one by omitting it from its picker.

Proposed combination policy: every supplied allow condition must pass and any matching denial excludes the value. Omitted allow conditions impose no restriction; an explicitly empty allowed set permits nothing. Sets, intervals and predicates are possible forms, with exact representations and precedence still to agree. These rules concern eligibility, separate from display formatting and from a picker increment.

For ranges, distinguish boundary eligibility from eligibility of covered values. An exclusive end may legally coincide with the beginning of an excluded period. Endpoint checks do not prove that the interval contains no blocked values. Whole-interval policies need an appropriate range rule/provider; arbitrary continuous or unbounded intervals cannot be validated by sampling or enumerating displayed values. Async availability and server reservation guarantees remain separate concerns.

Source feasibility review supports the map/predicate direction with adapter work. Recommended performance contract: compile enumerations to indexed canonical-value lookups; keep callbacks synchronous, side-effect-free and inexpensive; evaluate visible concrete candidates and actual field values, not the entire domain. Any caching must invalidate when rules, relevant reactive inputs, selected date, timezone, precision or range context change. Cache invalidation API remains open. Remote calls belong in an availability provider that supplies a current snapshot, not inside render-time predicates.

A full datetime predicate does not efficiently answer whether any allowed time exists in a day. Without a supplied summary/index, do not disable a whole date merely because the currently selected time is disallowed, or exhaustively scan all seconds to infer it. Keep navigation into unknown groups possible and validate concrete selections; optional date/hour summaries or indexed allow sets can provide stronger pruning. Likewise, require whole-range validation for blocked interiors rather than running unbounded scans on every render. Performance acceptance must measure callback counts and browser interaction on representative devices; no responsiveness guarantee is established by source inspection.

## Implementation responsibility and acceptance

Backends own presentation, native integration, focus/keyboard behavior and accessible grouping. They adapt native range normalization, date objects and partial-state behavior to the shared contract. Strong native datepicker support does not establish all range, codec or timezone guarantees.

Verify strict dates/leap days, time precision, codec round trips, canonical/display separation, unfinished drafts, reset/dirty/submission, no date-only timezone shifts, zoned datetime gaps/overlaps/conflicts, allow/deny combinations, blocked range interiors, inclusive date and exclusive time/datetime boundary behavior, overnight inference and the 24-hour limit, open-end options and malformed endpoints. Browser acceptance covers names/feedback, field and endpoint focus, keyboard/IME editing, locale/format changes, mobile/RTL and popup hosting. Verify physical presentation in a real browser in addition to core and DOM behavior.
