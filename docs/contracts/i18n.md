# Internationalization contract

Built-in internationalization is required. Live changes of formatting locale during unfinished editing are outside the shared handling guarantee and are application-managed. Application-scoped resource selection, native synchronization and Intl-backed message functions are implemented; see the guide below.

## Business concept

An interface can use one language for messages and a different locale for formatting. Business facts such as currency and time zone are separately expressible. For example, an amount field can have English labels, German number formatting, and a USD value.

## Responsibilities

- The application supplies language and formatting context, and business facts such as currency and time zone. Uninterface must not infer business currency or time zone merely from interface language.
- Uninterface provides shared translation, formatting, and codec support, including translation of built-in control messages.
- Reusable business components can supply their own translation resources.
- Implementations use this shared context and preserve the meaning and accessibility of messages, labels, values, and feedback across presentations.

Supported language and locale updates preserve control state, subject to the editing boundary below. The presentation may update translated text and formatted values without implicitly clearing selection, resetting a form, or ending its editing session. Business-owned control lifetime remains governed by the [UI state contract](ui-state.md).

## Formatting locale during editing

Applications should avoid changing the formatting/parsing locale while locale-sensitive input is partially edited. Uninterface is not required to supply a general migration mechanism for unfinished text or to resolve its interpretation across locales.

An application that needs this transition owns its handling. It can, for example, defer the locale change until editing finishes, or explicitly resolve the draft before changing context. These are illustrative application policies, not mandatory library operations. The application must arrange a coherent transition rather than rely on automatic reinterpretation.

Changing translated interface text without changing the input's parsing locale is a separate concern. This boundary does not remove ordinary translation, locale-aware formatting, or codec support from scope.

The [number codec](../api/functions/createUiNumberCodec.md) keeps its configured locale for the draft session. Its formatting locale selects decimal syntax, while its issue descriptors follow the application's message language. [Read-only money formatting](../api/functions/formatUiMoney.md) takes currency and scale explicitly.

## Implemented application service

See [localization and icons](../guides/localization-and-icons.md) for registration, BCP 47 normalization, script-aware fallback, asynchronous activation, native toolkit mapping and per-app context. Built-in packs are en, zh-Hans, zh-Hant and ar (Arabic), with script-derived RTL direction. Capability checks and initialization belong to application setup, not a UI wrapper. Message descriptors preserve translatable validation identity. Formatting locale remains separate from interface locale.

Core prepares the nine messages in `uninterface.common` at startup. The other built-in messages load by feature. Views prepare their message dependencies for the active language and retain them for their lifetime, including while cached by Vue KeepAlive. A language change prepares all packs needed by those views before activating the new language. Existing `uninterface` descriptors continue to resolve through their underlying feature pack. [Built-in message packs](../guides/localization-and-icons.md#built-in-message-packs)

Namespace authoring is supplied by `defineUiI18n<Key>(namespace)`: a stateless definition exposes `useI18n()` and standalone `msg(key, params?)`. Hook translators expose `t`, `lt` and `msg` with matching key/parameter restrictions. `msg` preserves unresolved identity for the consuming application; `t` resolves immediately and `lt` defers text against the owning application. Definition and descriptor creation require no injection, locale or resource lookup. Resource registration remains application-owned. Parameters retain their references and the existing string/number dictionary contract; per-key parameter inference is not implemented. See the [typed application helper](../guides/localization-and-icons.md#typed-application-helper).

Language resources do not establish full RTL compatibility. Integration with an application’s external localization engine is application-owned; supported built-in packs are listed in the localization guide. Currency/time zone stay explicit; native/browser-owned UI language limitations must be documented.
